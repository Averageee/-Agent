# 02 方案

## 调用流程

```
请求 ── 校验失败 ──▶ incomplete(invalid_input)，不调用工具
  │
  ├─ 幂等键命中已保存方案 ──▶ completed(idempotent_hit)，不调用工具
  │
  ▼
loop（每次运行最多 max_steps 步）
  模型.decide(state, messages) ─▶ Decision(action, args, reason)
  ├─ 业务工具 ─▶ 执行（可能被注入故障）─▶ 记录 Step(success/partial/failed) ─▶ 结果回传模型
  ├─ finish  ─▶ 护栏：只有 save_plan 成功后才接受，否则 rejected 并告知模型
  ├─ give_up ─▶ incomplete(gave_up)，带 gap
  └─ 其他    ─▶ rejected，提示模型重新选择
每步后持久化 RunState；到达上限 ─▶ incomplete(max_steps_reached)
```

代码：`src/content_agent/agent.py` 的 `_loop` / `_apply`。

## 动态决策

决策只由模型做，代码不预设工具顺序。模型看到的是系统提示词、请求（含可用工时）和每次工具返回。典型调整：

| 观察到 | 下一步 |
|---|---|
| 估算超预算或超工期 | 改选次优素材并重新估算（示例 05：M01=12 → M02=8） |
| 所有候选都不可行 | give_up，gap 给出最低费用、预算差额（示例 06） |
| AI 脚本引擎失败 | 改用模板引擎；费用结构变了，先重新估算再生成（示例 04） |
| 两种引擎都失败 | give_up，保留已成功的检索与估算，提示可续跑（示例 07） |
| 检索只部分成功 | 只在返回的素材中规划（示例 08） |
| 检索连续 2 次失败 | give_up |

## 状态

`RunState` 记录请求、幂等键、尝试次数、每个 Step（动作、参数、状态、结果、错误、摘要、决策依据）和模型对话，每步写入 `.agent_data/runs/<run_id>.json`。工具结果带 id（`est_1`、`scr_1`），`save_plan` 必须引用成功步骤的 id，所以失败步骤无法被当作成功使用。

## 护栏（代码强制，不依赖模型）

- 输入校验在循环前完成。
- `save_plan` 校验：估算与脚本都来自成功步骤；三者素材一致；估算引擎与脚本引擎一致；不超预算、不超工期。
- `finish` 只在方案保存成功后接受。
- 单次运行步数上限（默认 12）；模型调用异常返回 incomplete(llm_error)。
- 费用只以 `estimate_cost` 返回为准：素材授权费 + 脚本引擎费用；工时 = 制作工时 + 引擎工时；可用工时 = (deadline − today) 天 × 8。

## 幂等与续跑

- 幂等键 = sha256(主题小写, 预算, 截止日)，前 16 位。方案按键保存，已存在则直接返回，`save_plan` 内部也再次检查，不会覆盖。
- `--resume <run_id>`：读取状态，尝试次数 +1，向模型说明“已成功步骤有效，只补做失败步骤”，继续同一循环，步数上限重新计算。已完成或输入无效的运行不会重跑。

## 模型接入

- `OpenAICompatLLM`：用 `urllib` 调 `/chat/completions`，工具以 function calling schema 提供，每个工具都要求 `reason` 参数，作为 Trace 中的“决策依据”（不记录模型内部思维）。一次只取第一个 tool call。
- `MockLLM`：只读 RunState 中的观察结果决定下一步的规则策略，接口与真实模型相同。它本质上是条件分支，用来离线验证循环、状态与护栏，不代表模型决策。

## 技术取舍

| 选择 | 理由 | 代价 |
|---|---|---|
| 原生实现，不用框架 | 循环、状态、护栏都在 300 行内可读；续跑需要完全控制状态 | 没有现成的可视化与重试策略 |
| 无第三方运行依赖（urllib） | 离线即可运行，评审零配置 | 未处理流式、重试等特性 |
| 护栏放在代码而非提示词 | 模型出错时也不会超预算保存或把失败当成功 | 护栏规则需和业务表同步维护 |
| 按请求做幂等 | 重复提交不重复计费 | 想对同一请求重新规划需换 workdir |
| 故障只在进程内生效 | 续跑天然模拟“故障已恢复” | 无法模拟跨进程的持续故障 |
